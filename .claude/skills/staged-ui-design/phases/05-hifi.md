# 阶段 5：高保真

**本阶段只回答**：照着线框做出来的页面，是否符合项目的设计规范、用起来顺不顺。
**本阶段不谈**：导航结构和页面布局该不该换。发现它们有问题，回到阶段 2 或阶段 4 去改，不在代码里悄悄换一套。

## 入口

- 全部批次的线框都已过关（阶段 4）。后一批线框可能推翻前一批的布局，所以不和线框交替着做。用户明确要求某一批先做时照做，并把这个风险记入未决项。
- 处理前面留下的「留待阶段 5」条目。
- 项目有设计规范和组件库。没有的话，先停下来和用户把视觉方向定下来，这不在本 skill 的范围里。
- 重读项目的设计规范文档。视觉上的一切以它为准，不要带入自己的偏好。

## 第一步：组件映射

动手写代码之前，先列一张表：线框里的每个区块 → 用项目里现有的哪个组件。

- 自己去组件目录里查，不问用户「有没有表格组件」。
- 映射不上的列为缺口，每个缺口写清楚：需要什么、现有组件为什么不行、打算怎么补（组合现有组件 / 新增一个）。
- 把缺口一次给用户看，同意了再新增。大多数「缺口」其实可以用现有组件组合出来，新增组件是例外。

有了组件库，线框加这张映射表就足够开工，不需要在画布上再画一遍高保真稿：那样会有两份事实，改一处忘一处。

## 第二步：实现

- 用项目自己的技术栈和现有组件，在代码里做。跑起来的应用就是可以点的原型。
- 一批三到五页，过了关口再做下一批。
- 颜色、间距、圆角一律用项目的设计令牌，不写一次性的值。
- 数据：项目有可用的接口就接真实接口；没有或起不来时用假数据，并提供切到加载中、出错、没有数据三种状态的办法。用的是哪一种写进关口汇总。
- 线框里没定的细节（加载中、出错、没有数据时显示什么）在这里定，照项目设计规范的要求。
- 遵守仓库自己的开发规则（分支、测试、提交）。

## 评审

**一、验收清单**
项目的设计规范里有验收清单就用它的。没有的话，至少查这些，每一项都要在跑起来的应用里实际看到，截图为证：
- 深色和浅色主题（项目支持的话）
- 窗口变窄时（有可收起的侧栏就连收起状态一起看）
- 文字很长时
- 加载中、出错、没有数据三种状态，加载中不能显示成「没有数据」
- 只用键盘能走完核心任务，焦点看得见

没法自己截图时（没有浏览器工具、应用起不来），不要用读代码代替。在关口汇总里列出没验证的项，请用户按清单自己看并逐项回复，用户的回复等同截图。

**二、线框阶段没法评的四条启发式**
做法和记录格式见 `references/review-methods.md` 的「启发式评估」一节，先读它。
- 系统在干什么，用户看得到吗（进度、保存成功、后台任务状态）
- 出了错，提示说得清原因和下一步吗，能恢复吗
- 需要帮助的地方有没有就地的说明
- 容易出错的操作有没有确认和校验

**三、用户走任务**
请用户在跑起来的应用里，按任务清单把核心任务亲手走一遍。标准流程里这一步是找真实用户做可用性测试；这里用「用户本人走任务」代替，范围小得多，在关口汇总里写明这一点。项目有条件找真实用户时，建议用户去做。

**预筛**：派一个没参与实现的子代理，给它应用的访问方式（或截图）、线框、设计规范、任务清单和流程图（阶段 3 被裁时给你拆好的步骤），查前两项。问题分三级；启发式问题先按 0–4 定严重度再归级：
- 阻断（严重度 4，或核心任务走不通、状态显示有误导）
- 必须改（严重度 3，或违反设计规范、某种状态没处理）
- 以后再说（严重度 2 及以下，不影响这次交付的改进）

**给用户的关口汇总**：这批做了哪几页，怎么打开；阻断和必须改的问题；本批未覆盖的步骤；和线框不一致的地方及原因；没能验证的验收项；请用户走任务并决定过、改、还是回退。

**判定**：过关 = 没有阻断和必须改的问题，验收清单每项有截图或用户的逐项回复，未执行的评审有用户自己走的结果或用户明确同意不做，用户亲手走通了本批页面上的步骤并确认。最后一批时，用户把每条核心任务完整走通。

## 出口

所有批次过关后，回到 SKILL.md 的「阶段 6：收尾」。
