# 阶段 3：用户流程

**本阶段只回答**：完成每个核心任务要走哪几步，走不通时怎么办。
**本阶段不谈**：每一步的页面长什么样、放什么控件、用什么颜色。

## 入口

- 站点地图已经过关（阶段 2）。
- 处理前面留下的「留待阶段 3」条目。
- 先看同类成熟软件里同一个任务要几步、在哪里分叉，记进借鉴记录。

## 交付物：流程图

每个核心任务一张图（阶段 2 出口列明可以不画的除外）。

- 节点是用户的动作、系统的反馈或判断，用站点地图里的名字称呼页面。
- **必须画出走不通的分支**，按任务适用的画。常见的有：校验失败、没有权限、数据为空；有审批的任务还有对方驳回；有后台任务的还有任务卡住或失败。只画顺利路径的流程图评不出问题。某一类对这个任务不适用时，在阶段文档里写一句「不适用 + 理由」。
- 一张图控制在 20 个节点以内。超了就把异常分支拆成单独的一张，或者把任务拆小。
- 节点文字一到四个词，不放表情符号和换行。

### 放在哪里

**Figma 可用时**：流程图放 FigJam，阶段文档里放链接。
- 动手前先用 Figma MCP 的 skill 读取工具，现读官方的流程图生成 skill，照它当前的要求做。读不到时告诉用户，退到仓库方式。
- 下面几条是写这份文件时的工具行为，和现读到的官方 skill 不一致时以官方为准：
  - 用 Mermaid 的 flowchart 写，交给图表生成工具。同一轮设计的所有流程图放进同一个文件：第一次生成后记下文件标识，之后每次都传它，否则每次都会新建一个文件。
  - 图表生成工具不能逐个节点改。内容上的修改就改 Mermaid 重新生成，新图生成进同一个文件，旧图不删（用户的评论钉在旧图上），在对话里告诉用户哪张是新的。同一张图重生成两次还不对，停下来问用户，不要一直试。
  - 用评论读取工具读回未解决的评论。工具不能替你回复或把评论标为已解决。
- 把文件链接给用户，请他们直接在图上评论。改完后在对话里给一张对照表：哪条评论 → 改了什么（或为什么不改），请用户自己去点「已解决」。

**Figma 不可用时**：把 Mermaid 写在阶段文档的正文里，一任务一节，评审在对话或 PR 评论里做。

## 评审：流程评审

流程图上没有界面，所以这一关不问「用户看不看得到按钮」（那是线框阶段的事），只查四样。记录格式见 `references/review-methods.md` 的「流程评审」一节。

1. **步数**：从起点到完成要几步，有没有可以合并或省掉的。
2. **死路**：有没有走进去就出不来的节点，每个判断的每个出口都有去向。
3. **回退**：走错了或改主意了，能不能回到上一步，会不会丢掉已经填的东西。
4. **异常分支**：上面列的几类情况，每张图逐类有分支，或写明了不适用。任务清单里「做错的后果」写得重的任务，不允许整类缺失。

另外核对一致性：图上出现的每个页面，站点地图里都有；没有就说明站点地图漏了，回阶段 2 补。

**预筛**：派一个没参与画图的子代理，给它流程图的 Mermaid 源文、站点地图和任务清单，按上面四样逐张查，只报问题。和借鉴记录里同类软件步数的对比由你自己在关口汇总里补一句，不交给子代理。

**判定**：过关 = 没有死路，没有回不去或返回会丢掉已填内容的节点（允许用户明确接受并记入未决项），每张图的每类异常情况都有分支或写明不适用，图上的页面都在站点地图里，用户确认每张图。步数偏多只作为意见列出，由用户决定改不改。

## 出口

在阶段文档的「下一阶段的输入」里写：流程经过了哪些页面，哪些页面被多个任务共用（它们是线框阶段最该先画的），每个页面上要完成哪些步骤。
